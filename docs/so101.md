# SO-ARM101 generalist checkpoints

The `molmoact2_so101`, `pi05_so101`, `groot_so101` and `g05_so101` VLA adapters connect
Colosseum's local protocol to four SO100/101 generalist checkpoints. They
require `robot_type: so101` and 6-D absolute `joint_position`; the Client owns
the arm and cameras. See the [Client SO101 guide](../../colosseum-client/docs/so101.md)
for hardware configuration and shutdown behavior.

| Adapter | Checkpoint | Worker transport | Model chunk |
| --- | --- | --- | --- |
| `molmoact2_so101` | [allenai/MolmoAct2-SO100_101](https://huggingface.co/allenai/MolmoAct2-SO100_101) | HTTP `/act`, JSON NumPy | 30 |
| `pi05_so101` | [hqfang/pi05-so100_101](https://huggingface.co/hqfang/pi05-so100_101) | HTTP `/act`, JSON NumPy | 50 |
| `groot_so101` | [hqfang/groot-so100_101](https://huggingface.co/hqfang/groot-so100_101) | HTTP `/act`, JSON NumPy | 40 |
| `g05_so101` | [OpenGalaxea/G05](https://huggingface.co/OpenGalaxea/G05), `g05-so101/` | upstream WebSocket, MessagePack | served per step |

## Contract

- State and actions are `shoulder_pan, shoulder_lift, elbow_flex, wrist_flex,
  wrist_roll, gripper`: joint angles in degrees and gripper opening in [0, 100],
  as produced by LeRobot's `so101_follower`.
- **Joint frame.** The Client reports LeRobot's current calibration frame. These
  checkpoints were trained on datasets in LeRobot's earlier SO100 frame, so the
  adapter sends `model = sign * state + offset` with signs `[1,-1,1,1,1,1]` and
  offsets `[0,90,90,0,0,0]`, and converts returned actions back; see
  [LeRobot backward compatibility](https://huggingface.co/docs/lerobot/backwardcomp).
  Without it, shoulder_lift and elbow_flex are far outside the training range.
  A checkpoint fine-tuned on current-frame data needs
  `backend_options.joint_frame: current`.
- `head_image` is the external camera and `left_image` the wrist camera; change
  them with `backend.options.external_sensor` / `wrist_sensor`. Images are RGB
  uint8 at the Client's resolution; each model resizes them itself.
- A chunk longer than the registered `max_horizon` is truncated; the Client then
  requests a new chunk from a fresh observation.
- The example registers `max_horizon` 30 for MolmoAct2 and G05, 50 for pi0.5 and
  40 for GR00T, each model's own chunk length. Use the values of your Router registration.

## Model workers

Use one environment per model and install this package into each with
`--no-deps`, as for the [DROID workers](droid-inference.md). Workers load local
snapshots offline; download the revision registered on your Router first.

### MolmoAct2-SO100_101

```bash
colosseum-policy-model molmoact2 --robot-type so101 \
  --checkpoint /path/to/MolmoAct2-SO100_101-snapshot --device cuda:0 --dtype bfloat16 --port 9201
```

Uses `norm_tag=so100_so101_molmoact2`, images `[external, wrist]`, continuous
actions, no depth reasoning and no CUDA graph. The fp32 snapshot is about 21 GB;
bfloat16 needs about 11 GB of GPU memory. This snapshot's model source already
contains the bfloat16 fixes, so `--patch-molmo-bf16` is not needed.

### pi0.5 SO100/101

This checkpoint needs the patched LeRobot source it ships with:

```bash
git clone https://github.com/huggingface/lerobot.git && cd lerobot
git checkout b6ec0060779550c0a157ae34feb89e0cf86012a8
git apply /path/to/pi05-so100_101-snapshot/code/lerobot.patch
pip install -e '.[pi]'
```

```bash
colosseum-policy-model pi05_lerobot --robot-type so101 \
  --checkpoint /path/to/pi05-so100_101-snapshot --device cuda --port 9212
```

The worker uses the checkpoint's saved pre/post processors and bundled
SentencePiece tokenizer; `--tokenizer` and `--stats` are not needed. The external
image fills `camera_0`, the wrist image `camera_1`; the remaining slots are zero
images flagged as padding.

### GR00T N1.7 SO100/101

A LeRobot policy checkpoint, not a raw Isaac-GR00T one. It needs a LeRobot with
the GR00T N1.7 policy (tested with 0.6.1) and a local snapshot of the base model
[nvidia/GR00T-N1.7-3B](https://huggingface.co/nvidia/GR00T-N1.7-3B), revision
`2fc962b973bccdd5d8ce4f67cc63b264d6886495`, which the loader initializes from.

```bash
colosseum-policy-model groot_n17 --robot-type so101 \
  --checkpoint /path/to/groot-so100_101-snapshot \
  --base-model /path/to/GR00T-N1.7-3B-snapshot --device cuda --port 9217
```

The worker uses the checkpoint's saved pre/post processors and bundled
`vlm_processor/`; `--processor` is not needed. The external image fills
`camera_0` and the wrist image `camera_1`. The other two slots are omitted, not
zero-padded: the model card asks for padded slots to be removed before VLM
tokenization, and LeRobot 0.6.1 has no padding flag for this policy. About
14 GB of GPU memory, about 0.12 s per 40-step chunk after a warm-up call at load.

### G05 SO100/101

Install upstream [GalaxeaVLA](https://github.com/OpenGalaxea/GalaxeaVLA) under
its license and download `g05-so101/`, `action_tokenizer.pt` and
`qwen3_5_2b_base_processor/`. The run config resolves the tokenizer and
processor relative to the upstream source root.

```bash
colosseum-policy-model g05 --robot-type so101 --source-root /path/to/GalaxeaVLA \
  --checkpoint /path/to/g05-snapshot/g05-so101/checkpoints/model_state_dict.pt \
  --device cuda --action-steps 30 --port 9204
```

This runs upstream `scripts/serve_policy.py` with `eval_embodiment=so100`.
`--action-steps` is how many steps the server serves per inference; set it to
the registered `max_horizon`. Add upstream Hydra overrides with repeatable
`--g05-override KEY=VALUE`. The adapter sends `exterior` and `wrist_right`
images plus a zero `wrist_left` (`backend_options.padded_cameras`), then drains
the cached chunk over the same connection.

## Colosseum local server

```bash
uv sync --extra droid
cp configs/local-runtime-so101.yaml.example configs/local-runtime-so101.yaml
# Replace the /path/to placeholders; keep revisions and contracts equal to the Router's.
uv run colosseum-policy-local --config configs/local-runtime-so101.yaml
```

Only one model is loaded at a time: the runtime stops the previous worker before
starting the one assigned to the next trial.

Tests cover the adapter with loopback HTTP and WebSocket services, frame
conversion, routing and the worker command line. They load no weights and do
not establish task success on any rig.

## Mixed VLA and LLM evaluation with SO101 EEF control

Use [local-runtime-so101-mixed-eef.yaml.example](../configs/local-runtime-so101-mixed-eef.yaml.example)
with `backend.name: auto`. Keep the VLA entries and add only LLM models that
the Router has registered for the same six-value public `joint_position`
contract. The Router still chooses the model. The `inspect_agent` backend gives
LLMs a seven-value `eef_delta_pose` interface, while VLA models keep their
joint-position adapters. The Client converts EEF deltas to accepted joint
commands using the calibrated SO101 URDF and records those commands in its
existing LeRobot export and upload pipeline. Inspect's review interface is not
part of this flow.
LLM and VLA entries may have different `control_hz` values. The Router's LLM
`control_hz` controls the agent session and Client pacing; the local LLM entry's
rate is only a required configuration value. All other public fields must match
the Router's model descriptor exactly. Use `model.name` from the Router's run
preparation, which may differ from the leaderboard's `policyId`.
If a Router registration uses a relay URL or a rig-specific suffix in its LLM
model name, retain both in the model's public `name` and `url`. Set per-model
`backend_options.api_base_url` to the matching official provider API, and
`backend_options.api_model` to the provider's model ID without the rig suffix.
The Policy Server matches the Router's public contract, then sends inference
directly to the official endpoint. Claude Code account sessions use the official
Claude CLI and the configured `api_model`; they do not call the relay.

Install the agent extra in the Policy Server environment and start the mixed
runtime with the example after filling the Router model identities, revisions,
worker paths, and rig notes:

```bash
uv sync --locked --extra agent
cp configs/local-runtime-so101-mixed-eef.yaml.example configs/local-runtime-so101-mixed-eef.yaml
uv run --no-sync colosseum-policy-local --config configs/local-runtime-so101-mixed-eef.yaml
```

For direct API access, set `llm_api_keys` on the Client and use each provider's
official `api_base_url` in the corresponding LLM entry. For an Anthropic account
login, configure `llm_account_logins.anthropic: claude-code` on the Client and
run the official Claude CLI on the Policy Server host. If `claude` is not on
`PATH`, use its absolute path for `auth status` or `auth login`, and set the same
path as `backend.options.llm.claude_command` in the runtime YAML. For example,
this rig has the CLI at
`/home/magiclab/inspect-robots/.so101/claude-cli/claude_agent_sdk/_bundled/claude`.
Run `auth status` first; only run `auth login` if it reports that the account is
logged out. Do not configure an Anthropic API key at the same time.
The Client-to-Policy-Server connection must be WSS or a loopback WebSocket.

The EEF bridge has software unit tests but has not been validated on a physical
arm in this repository. Check the URDF, calibrated joint limits, cameras and
the LeRobot `max_relative_target: null` setting on the actual follower before
running a live trial. Router `max_horizon`, `control_hz`, and task `max_steps`
govern EEF trials; the local EEF bridge adds no displacement step cap.
